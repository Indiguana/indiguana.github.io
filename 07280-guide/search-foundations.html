Search problems, BFS, DFS & UCS

By the end of this page you can take any planning puzzle, write it down as a formal search problem, and hand-trace breadth-first, depth-first and uniform-cost search on it — including the frontier bookkeeping step that everyone gets wrong.

Why this page exists

The Lecture 2 slides open with “Pre-reading: tree search vs graph search, BFS, DFS, UCS” and then spend four slides reviewing them before racing off to heuristics. If you never did the pre-reading, the rest of the search unit is built on sand. This chapter rebuilds the whole foundation from scratch, at the level of Russell & Norvig chapter 3, and then walks the exact slide examples line by line.

1. What a search problem actually is

Start concrete. You are Pacman. You are standing somewhere in a maze. You want to reach a dot in the far corner. You cannot see the whole maze at once and you certainly cannot list every possible future — but at every moment you can answer three local questions:

  • Where am I right now?
  • What moves are legal from here?
  • If I take one of those moves, where do I end up, and what did it cost me?

That is it. Every search problem in this course is nothing more than those three questions, written down formally, plus a way to recognise when you're done.

Definition — search problem

A search problem consists of:

  • a state space — the set of all configurations the world can be in, as far as our problem cares;
  • for each state $s$, a set $\text{Actions}(s)$ of allowable actions;
  • a transition model (successor function) $\text{Result}(s,a)$ — the state you land in if you do $a$ in $s$;
  • a step cost function $c(s,a,s')$ — the cost of the single action $a$ that took you from $s$ to $s' = \text{Result}(s,a)$;
  • a start state $s_0$ and a goal test — a predicate $\text{IsGoal}(s)$ that returns true or false.

A solution is a sequence of actions — a plan — which transforms the start state into a goal state. An optimal solution is one of minimum total cost.

Read the symbols out loud once, because they will appear on every later page:

  • $s$ and $s'$ are states, not numbers. In a maze, $s$ might be the pair “(row 3, column 7)”.
  • $a$ is one action, e.g. North. $\text{Actions}(s)$ is the whole legal menu at $s$; in the slide's little picture that menu is $\{\mathrm{N}, \mathrm{E}\}$, because walls block the other two.
  • $\text{Result}(s,a)$ is a function: one state in, one action in, one state out. Deterministic. (Chapter 3 breaks this when we add a random ghost and need expectimax.)
  • $c(s,a,s')$ takes all three arguments because the same action can cost different amounts from different places — walking north over gravel is not walking north over ice. In the slide's picture every step costs $1$.

Notice what is not in the definition: there is no map, no picture, no global view. A search algorithm is only ever allowed to call $\text{Actions}$, $\text{Result}$, $c$, and $\text{IsGoal}$. Everything the algorithm knows, it discovered by poking those four functions.

Analogy

You are in a pitch-dark building with a phone that can answer exactly two queries: “what doors are in this room?” and “if I go through door k, which room am I in and how many steps did it take?”. Search algorithms are strategies for exploring that building with only those queries. Where the analogy breaks: unlike you, the algorithm can teleport — it keeps a list of half-explored rooms and may jump back to any of them at no cost. Real robots pay to backtrack; our search algorithms do not, because they are planning on a model before moving at all.

A solution is a plan, not a state

This trips people up on exams. If the question asks “what is the solution?”, the answer is an action sequence — [North, North, East, East] — or equivalently the path of states it induces, S → A → C → G. The answer is never just “the goal state”; we already knew what the goal looked like. The whole point was the route.

Common mistake

“The answer is $G$.” No. $G$ was given to you in the goal test. Search is the process of recovering the plan, and later in this chapter you will see that we recover it by following parent pointers back from the goal node, not by remembering paths as we go.

2. World states, search states, and how big the space is

Here is the slide that looks like arithmetic and is really about modelling. Pacman in a small maze:

  • Food count: 30
  • Ghost positions: 12
  • Agent facing: N, S, E, W

Every symbol, named:

  • $p$ — Pacman's position, one of the 120 non-wall squares.
  • $f_i$ — a boolean: is dot $i$ still on the board? There are 30 dots, so $2^{30}$ combinations of eaten/uneaten. (This is why it's $2^{30}$ and not $30$: the 30 is a count of bits, not a count of states.)
  • $g_1, g_2$ — the positions of the two ghosts. Each ghost can be in any of 12 squares, so $12 \times 12 = 12^2$.
  • $d$ — the direction Pacman is facing, 4 possibilities.

Multiply: $120 \cdot 2^{30} \cdot 144 \cdot 4 \approx 7.4 \times 10^{13}$. Seventy-four trillion. No computer is going to enumerate that.

Why the representation shrinks when the task shrinks

The magic is in the second and third rows. For the task “eat the dot in the top-left corner,” the state is just $(p)$ — 120 states. We threw away 99.9999% of the world. Why is that legal?

Key idea — a state must record exactly what affects the future

A variable belongs in your state representation if and only if (a) it changes as you act, and (b) the rest of the problem — legal actions, costs, or the goal test — depends on it. Anything else is decoration and you must drop it, because every bit you keep multiplies the size of the space by 2.

Apply the test to “eat the top-left dot”:

  • Ghost positions? The goal test is “is Pacman standing on the top-left square?”. Ghosts don't block movement and we're not modelling dying. Drop them — factor of $144$ gone.
  • Which dots are eaten? The goal only mentions one specific square. Whether we happened to swallow other dots on the way changes nothing about what we can do next or when we're finished. Drop it — factor of $2^{30}$ gone.
  • Facing direction? Legal moves don't depend on it (Pacman can reverse freely) and the goal doesn't mention it. Drop it — factor of $4$ gone.
  • Position? Obviously keep it. $120$ states.

Now “eat all dots”. The goal test is “are all 30 $f_i$ false?”. That mentions the food, so the food must stay in the state: $120 \cdot 2^{30} \approx 1.3 \times 10^{11}$. Ghosts and facing are still irrelevant, so they still go.

Intuition

The state is the memo you would leave yourself if you were teleported out of the game and back in an hour later, containing everything you'd need to carry on optimally. For “reach the corner,” the memo says only “you are at square 47.” For “eat everything,” it must also say which dots are already gone — otherwise you'd wander back over empty squares forever.

World state vs. search state

Definition — abstraction

A world state contains every detail of the actual environment (pixel positions, score, which frame of the animation the ghost is on). A search state contains only the details our search problem needs. Choosing the search state is called abstraction, and the slide's phrase for it is “vertices are (abstracted) world configurations.”

Abstraction is the single highest-leverage decision in applied search. The algorithms in this chapter are fixed and about ten lines long; the difference between a solver that runs in a millisecond and one that never finishes is almost always the state representation. A good abstraction must be sound: every plan that works in the abstract problem must correspond to a plan that works in the real one.

Guided problemSizing three Pacman variants

Same maze as the slide: 120 legal squares, 30 dots, 2 ghosts each in one of 12 squares, 4 facings. Give the state representation and the state-space size for each task.

  1. (a) “Reach the bottom-right corner without ever being caught by a ghost”, where ghosts move and catching means sharing a square.
  2. (b) “Eat all 30 dots” in a version where Pacman can only turn left or go straight (no reversing).
  3. (c) “Eat the 4 power pellets (a subset of the 30 dots), in any order.”
Step 1 — Run the relevance test on each variable

For each of $p$, the $f_i$, $g_1,g_2$ and $d$, ask: does this task's goal test, action set, or cost function read that variable? If the variable is read anywhere, or if it changes in a way that later affects one of those, it stays.

Step 2 — (a) the ghost-avoiding walk

The goal test reads only $p$. But the legality of the plan now depends on where the ghosts are — “caught” is defined by $p = g_i$ — so ghost positions are read by the problem. Food is never read; facing is never read.

State $= (p, g_1, g_2)$, size $120 \cdot 12 \cdot 12 = 120 \cdot 144 = \mathbf{17{,}280}$.

Still tiny. This is the classic lesson: adding adversaries costs you a polynomial factor, adding memory of what you've collected costs you an exponential one.

Step 3 — (b) all dots, but no reversing

The goal test reads all the $f_i$, so keep the food bits: $2^{30}$. New wrinkle: $\text{Actions}(s)$ now depends on which way you are facing, because “go straight” and “turn left” are defined relative to $d$. Since the action set reads $d$, $d$ is now part of the state.

State $= (p, f_1,\dots,f_{30}, d)$, size $120 \cdot 2^{30} \cdot 4 \approx \mathbf{5.2 \times 10^{11}}$.

Moral: a rule change that doesn't touch the goal can still force a variable back into the state, through the action set.

Answer & the takeaway

(c) Only 4 of the 30 dots are ever read by the goal test, so you only need 4 booleans, not 30:

State $= (p, f_{i_1}, f_{i_2}, f_{i_3}, f_{i_4})$, size $120 \cdot 2^4 = 120 \cdot 16 = \mathbf{1{,}920}$.

Takeaway: $10^{11}$ became $10^3$ purely by noticing that 26 of the booleans are never read. Before you optimise an algorithm, delete a variable.

In the “eat all dots” representation the size is $120 \times 2^{30}$. Why $2^{30}$ rather than $30$, or $30!$?
Why: The state is a snapshot, not a history. It doesn't record the order you ate dots in (that's the plan, not the state) — only the current configuration, which is one boolean per dot. Order matters for cost, but not for identifying the state, which is exactly what lets two different plans meet at the same state and be compared.

3. State space graphs vs. search trees

Two pictures, constantly confused, drawn from the same problem.

Definition — state space graph

The state space graph is a mathematical representation of a search problem: vertices are the (abstracted) world configurations, edges are transitions resulting from actions, edge weights are step costs, and the goal test picks out a set of goal vertices (maybe only one). In a state space graph, each state occurs exactly once.

We can rarely build this full graph in memory — the Pacman graph has $10^{13}$ vertices — but it is the right mental object.

Definition — search tree

The search tree is what an algorithm actually builds. Its root is the start state. Each node corresponds to a path from the start, and its children are the results of the legal actions at the end of that path. A state appears once in the graph but once per path in the tree.

The relationship is: the search tree is the graph unrolled along every path. If two different routes reach state $B$, the graph has one $B$ and the tree has two nodes both labelled $B$ — different nodes, same state, different histories and (usually) different path costs.

Figure 1 · The graph on the left unrolls into the tree on the right
What to notice: the graph has one vertex B; the tree already has three nodes labelled B, one per distinct path (S-B, S-A-B, S-B-A-B). Because A and B point at each other, the tree never ends — a finite graph can unroll into an infinite tree. The only thing stopping it is an algorithm that refuses to re-expand a state it has already seen.
Key idea

Tree nodes are paths; graph vertices are states. The tree is infinite whenever the graph contains a cycle, even if the graph has three vertices. Everything called “graph search” below is just “tree search plus a memory of which states we already expanded.”

A state space graph has 8 vertices and no cycles at all (it's a DAG). How many nodes can the corresponding search tree have?
Why: No cycles ⇒ finitely many paths ⇒ a finite tree. But a DAG can have exponentially many distinct paths: a “diamond chain” of $k$ diamonds has $2k+1$ vertices and $2^k$ paths. You'll see this concretely in §11, where a 12-vertex graph unrolls into a 28-node tree that visits the state q four separate times.

4. The generic search algorithm

Every algorithm on this page — and greedy search and A* on the next page — is the same seven lines with one word changed. Learn the skeleton once.

The frontier

Definition — frontier and explored set

The frontier (also called the fringe or open list) is the set of nodes that have been generated but not yet expanded — the rim of what we know. The explored set (closed list) is the set of states we have already expanded. To expand a node means: take its state, call $\text{Actions}$ and $\text{Result}$, and put the resulting children on the frontier.

Analogy

Drop ink on paper. The explored set is the dried blot; the frontier is the wet rim creeping outward. All three algorithms below are the same blot — they differ only in which part of the rim gets to creep next. BFS creeps evenly; DFS shoots one tendril as far as it can; UCS creeps fastest where the paper is thinnest (cheapest).

Tree search

function TREE-SEARCH(problem) returns a solution, or failure
    initialize the frontier using the initial state of problem
    loop do
        if the frontier is empty then return failure
        choose a leaf node and remove it from the frontier      <-- THE ONLY CHOICE
        if the node contains a goal state then
            return the corresponding solution
        expand the chosen node, adding the resulting nodes to the frontier

The comment marks the entire design space of uninformed search. Choose the shallowest node and you have BFS. Choose the deepest and you have DFS. Choose the cheapest-so-far and you have UCS. Choose by $g+h$ and you have A*. That is the whole story.

Graph search

function GRAPH-SEARCH(problem) returns a solution, or failure
    initialize the frontier using the initial state of problem
    initialize the explored set to be empty
    loop do
        if the frontier is empty then return failure
        choose a leaf node and remove it from the frontier
        if the node contains a goal state then
            return the corresponding solution
        add the node's state to the explored set
        expand the chosen node, adding the resulting nodes to the frontier
            only if not already in the frontier or the explored set

Two lines added, one enormous consequence: the tree is now pruned so that each state is expanded at most once, which makes the search finite whenever the state space is finite. The cost is memory — the explored set can grow to the size of the whole state space.

Common mistake

“Graph search is strictly better, always use it.” Not quite. Graph search needs $O(|S|)$ memory for the explored set, which kills it on huge spaces (that $10^{13}$-vertex Pacman graph). And the “only if not already in the frontier” clause is the subtle one: for UCS and A* you may not simply discard a duplicate — you must compare costs and possibly replace. That replacement step is §10 of this page, and getting it wrong is the single most common error on this material.

What a node actually stores

From the slide “A Note on Implementation”. A node is a record with four fields:

FieldMeaningValue for a child of parent via action $a$
statethe state this node sits atResult(parent.state, a)
parentthe node we came fromparent
actionthe action taken to get herea
path-costtotal cost from the start to here; written $g(n)$parent.path_cost + c(parent.state, a, state)

The last row is the one to memorise, because it is the definition of $g$:

$$g(\text{child}) \;=\; g(\text{parent}) \;+\; c(\text{parent.state},\, a,\, \text{child.state}).$$

In words: the cost of a path is the cost of its prefix plus the cost of the one new step. $g(n)$ is often called the backward cost — what you have already spent to arrive at $n$ — in contrast to the forward estimate $h(n)$ you meet on the next page.

Why store parent instead of the whole path in every node? Memory. A million frontier nodes each holding a 40-step list is 40 million entries; a million nodes each holding one pointer is a million entries. To get the plan back:

Key idea — extracting the solution

Start at the goal node. Repeatedly follow parent, collecting the action field at each hop, until you reach the node whose parent is null (the start). Reverse the collected list. That's your plan.

5. Breadth-first search

Strategy: expand a shallowest node first. Implementation: the frontier is a FIFO queue.

FIFO = first in, first out. New nodes join the back of the queue; we always pop from the front. Because a node generated at depth $k$ always enters the queue after every node of depth $k$ or less that was generated before it, the queue drains depth 0, then all of depth 1, then all of depth 2… BFS sweeps the tree in complete tiers.

Analogy

A ripple on a pond. At time $k$ the wave front is exactly the set of states reachable in $k$ steps. Where it breaks: a real ripple travels at a speed set by physics — by distance. BFS's ripple travels by number of actions. If some actions cost 100 and others cost 1, BFS's ripple is no longer a circle in cost-space, and that discrepancy is exactly the reason UCS exists.

Properties, with the reasoning

Write $b$ for the branching factor (max children per node), $d$ for the depth of the shallowest goal, $m$ for the maximum depth of the tree (possibly $\infty$).

  • Complete? Yes, if $b$ is finite. Reason: any goal sits at some finite depth $d$; BFS finishes tier $d-1$ in finite time (each tier is finite because $b$ is), so it must reach the goal.
  • Optimal? Only when all step costs are equal (e.g. all $1$). Reason: BFS returns the goal with the fewest actions. If every action costs the same $c$, fewest actions = cheapest, so it's optimal. If costs differ, a 2-step path of cost $100$ is returned over a 3-step path of cost $3$. Not optimal in general.
  • Time: $O(b^d)$. Reason: it generates every node down to depth $d$, and $1 + b + b^2 + \dots + b^d = \dfrac{b^{d+1}-1}{b-1} = O(b^d)$ — the last tier dominates the sum, so the whole search costs the same order as its final tier.
  • Space: $O(b^d)$, and this is the killer. Reason: at the moment BFS is about to expand the first node of tier $d$, the frontier contains essentially all of tier $d$ — that's $b^d$ nodes held in memory at once.
Example — why $O(b^d)$ space is fatal

Take $b=10$, one million nodes generated per second, 100 bytes per node. At $d=12$: time $\approx 10^{12}$ nodes $= 13$ days; memory $\approx 10^{14}$ bytes $= 100$ terabytes. BFS runs out of RAM long before it runs out of patience. Remember this when you meet iterative deepening in alpha-beta: memory, not time, is usually what stops you.

6. Depth-first search

Strategy: expand a deepest node first. Implementation: the frontier is a LIFO stack.

Change one word — FIFO becomes LIFO — and the behaviour inverts. We push a node's children on top of the stack and immediately pop one of them, so the search plunges down one branch until it hits a dead end, then backs up one level and tries the next sibling.

Analogy

The maze-walker with a piece of chalk: always take the leftmost unexplored door; when you hit a dead end, walk back to the last junction with an unexplored door and take that. You need chalk for the current path only, not for the whole maze — which is precisely DFS's $O(bm)$ memory advantage.

Properties, with the reasoning

  • Complete? Tree-search DFS: no. One cycle in the graph and DFS walks $A, B, A, B, \dots$ forever, never noticing. Even without cycles, an infinitely deep branch traps it. Graph-search DFS on a finite space: yes — the explored set forbids revisiting states, so it must terminate.
  • Optimal? No, not in any sense. It returns the first goal it stumbles into, which may be arbitrarily deep and arbitrarily expensive.
  • Time: $O(b^m)$. Reason: in the worst case it explores the entire tree down to its maximum depth $m$ before finding anything. When $m \gg d$ this is dramatically worse than BFS; when the tree is shallow and goals are dense it can be far better in practice.
  • Space: $O(bm)$ — linear. Reason: the stack only ever holds the nodes on the current root-to-leaf path ($m$ of them) plus their unexpanded siblings ($b-1$ each). Nothing else is retained. This is the entire reason anyone still uses DFS.
Intuition — the trade in one line

BFS buys optimality-in-steps with exponential memory. DFS buys linear memory by giving up both optimality and (in cyclic spaces) completeness. Neither is satisfactory, which is why the next two sections exist: iterative deepening buys back BFS's guarantees at DFS's memory, and UCS buys back true cost-optimality.

7. Iterative deepening beyond syllabus

Not in the Lecture 2 slides — but it is standard pre-reading material (R&N §3.4.5) and alpha-beta pruning leans on it for move ordering, so here it is, briefly.

Run a depth-limited DFS with limit $0$. No goal? Run it again with limit $1$. Then $2$. Then $3$. Stop at the first limit that finds a goal.

function ITERATIVE-DEEPENING-SEARCH(problem) returns a solution, or failure
    for limit = 0, 1, 2, ... do
        result <- DEPTH-LIMITED-SEARCH(problem, limit)
        if result != cutoff then return result

Your first reaction should be that re-searching from scratch every round is wasteful. It isn't, and the arithmetic is worth seeing. Nodes generated by IDS down to depth $d$:

$$N_{\text{IDS}} = (d+1)b^0 + d\,b^1 + (d-1)b^2 + \dots + 1\cdot b^d,$$

because the root is regenerated $d+1$ times, tier 1 is regenerated $d$ times, and the bottom tier exactly once. Compare with BFS, which generates $N_{\text{BFS}} = b^0 + b^1 + \dots + b^d$. For $b = 10, d = 5$: $N_{\text{IDS}} = 123{,}456$ versus $N_{\text{BFS}} = 111{,}111$ — about 11% more work. In general the overhead factor tends to $\dfrac{b}{b-1}$, which for $b=10$ is $1.11$.

The reason is the same fact that made BFS's time $O(b^d)$: the bottom tier dominates, and IDS generates the bottom tier only once. So IDS is complete, optimal when step costs are uniform, runs in $O(b^d)$ time, and uses only $O(bd)$ memory. It is the standard choice for large uniform-cost spaces of unknown depth.

Analogy

A dog on an extendable leash. Let out one notch, let it sniff everywhere it can reach, reel it in, let out another notch. You re-walk the ground near the house many times — but the ground near the house is a vanishing fraction of the ground at full extension.

8. Uniform-cost search

BFS optimises the wrong thing: number of actions. Real problems have costs — time, fuel, money, risk. UCS fixes exactly this and nothing else.

Key idea

Strategy: expand a cheapest node first. Implementation: the frontier is a priority queue, with priority = cumulative path cost $g(n)$.

That's it. Same skeleton as BFS, different queue discipline. When all step costs are equal, $g(n)$ is proportional to depth and UCS degenerates into BFS.

Here is the course's pseudocode, from the slides:

function UNIFORM-COST-SEARCH(problem) returns a solution, or failure
    initialize the explored set to be empty
    initialize the frontier as a priority queue using g(n) as the priority
    add initial state of problem to frontier with priority g(S) = 0
    loop do
        if the frontier is empty then
            return failure
        choose a node and remove it from the frontier          <-- the MINIMUM-g node
        if the node contains a goal state then
            return the corresponding solution
        add the node state to the explored set
        for each resulting child from node
            if the child state is not already in the frontier or explored set then
                add child to the frontier
            else if the child is already in the frontier with higher g(n) then
                replace that frontier node with child

Three lines deserve a paragraph each.

“choose a node and remove it from the frontier”

Read this as pop the node with the smallest $g$. Ties can be broken arbitrarily; different tie-breaking gives different (equally optimal) answers.

“if the node contains a goal state then return”

The goal test happens on pop, not on generation. This is not a stylistic choice — it is required for optimality. A goal that is generated cheaply may still be sitting on the frontier with a bad $g$ that a later, better path will improve. Only when a goal node reaches the front of the priority queue do we know nothing cheaper remains.

“else if the child is already in the frontier with higher $g(n)$ then replace”

This is the decrease-key step, the one the walkthrough in §10 is built around. If we rediscover a frontier state by a cheaper route, we must upgrade its entry. If the new route is worse, we discard the new node and keep the old entry. And if the state is already in the explored set, we do nothing at all — §13 proves that this is safe because a popped node's $g$ is already optimal.

Properties, with the reasoning

Let $C^*$ be the cost of the optimal solution and $\varepsilon > 0$ a lower bound on any single step cost.

  • Complete? Yes, provided every step cost is at least some $\varepsilon > 0$ and a finite-cost solution exists. Reason: each expansion raises the contour by at least $\varepsilon$, so after finitely many expansions the frontier's minimum $g$ exceeds $C^*$ — impossible unless the goal was popped first. The $\varepsilon$ condition is not pedantry: with zero-cost actions UCS can loop forever inside a zero-cost cycle, expanding infinitely many nodes at $g = 0$.
  • Optimal? Yes — see the proof in §13.
  • Time and space: $O\!\left(b^{\,1 + \lfloor C^*/\varepsilon \rfloor}\right)$. Reason: UCS expands every node whose path cost is less than $C^*$. The cheapest such node is at least $\varepsilon$ per step, so the deepest one you could be forced to expand sits at depth about $C^*/\varepsilon$ — an “effective depth” that replaces BFS's $d$. When every step costs exactly $1$, $C^*/\varepsilon = d$ and the bound collapses back to BFS's $O(b^{d+1})$.
Common mistake

Writing UCS's complexity as $O(b^d)$. The depth of the goal is irrelevant to UCS; what matters is how many cheap nodes exist. A goal 2 steps away costing $1000$ is found only after UCS has expanded every node reachable for less than $1000$ — which may be millions of nodes at depth 500.

During UCS the goal state $G$ is generated and put on the frontier with $g = 11$. The frontier also holds nodes with $g = 6$ and $g = 9$. What does UCS do next?
Why: The goal test is on pop. Expanding the $g=6$ node might generate a cheaper route to $G$ — say $g=7$ — which then replaces the 11 on the frontier. This is exactly what happens in Figure 2: try the UCS mode and watch $G$ enter at 11 and get overwritten with 7. Returning at generation time would have given you the 11-cost answer and destroyed optimality.

Guided problemPredict all three answers before you press Step

Using the graph in Figure 2 (edges $S\!-\!A\,{=}\,1$, $S\!-\!B\,{=}\,6$, $A\!-\!C\,{=}\,2$, $A\!-\!E\,{=}\,4$, $C\!-\!D\,{=}\,2$, $D\!-\!G\,{=}\,2$, $E\!-\!G\,{=}\,6$, $B\!-\!G\,{=}\,3$; neighbours are tried in the order listed in the adjacency list $S\!:\![A,B]$, $A\!:\![S,E,C]$, $B\!:\![S,G]$, $C\!:\![A,D]$, $D\!:\![C,G]$, $E\!:\![A,G]$), predict:

  1. Which path does each of BFS, DFS and UCS return, and at what cost?
  2. How many nodes does each one pop before returning?
Step 1 — What is each algorithm actually minimising?

BFS minimises the number of edges. Look for the shortest path by hop count: $S\!-\!B\!-\!G$ is 2 hops; everything else is 3 or 4. So BFS must return $S\!-\!B\!-\!G$, whatever it costs.

DFS minimises nothing. It returns whatever it bumps into while diving. Follow the adjacency order: from $S$ it takes $A$ first; from $A$ it skips $S$ (explored) and takes $E$ first; from $E$ it takes $G$. Done — $S\!-\!A\!-\!E\!-\!G$.

UCS minimises total cost. Enumerate the four paths: $S\!-\!A\!-\!C\!-\!D\!-\!G = 1{+}2{+}2{+}2 = 7$; $S\!-\!B\!-\!G = 6{+}3 = 9$; $S\!-\!A\!-\!E\!-\!G = 1{+}4{+}6 = 11$; $S\!-\!B\!-\!D\!-\!G$ doesn't exist. So UCS returns the 7.

Step 2 — Count BFS's pops

Frontier as a FIFO. Pop $S$ → push $A(1), B(6)$. Pop $A$ → push $E, C$. Pop $B$ → push $G$. Pop $E$ → $G$ already on the frontier, skip. Pop $C$ → push $D$. Pop $G$ → goal.

10. The UCS walkthrough, and the step everyone gets wrong

This is the slide trace, reproduced exactly and then explained. The graph:

Figure 3 · The walkthrough graph (directed, as drawn on the slide)
Edges: $S\!\to\!A = 1$, $S\!\to\!B = 4$, $A\!\to\!C = 2$, $C\!\to\!D = 4$, $B\!\to\!D = 1$, $D\!\to\!G = 3$. Two routes reach $D$ — a short-hop expensive one through $C$ and a long-hop cheap one through $B$ — and the whole lesson lives in what UCS does when the second one shows up.

The slide's table, complete:

Frontier (added, with $g$)ExploredWhat happened
S: 0Sstart; pop $S$, expand it

The step you must understand: “replaced by a better path to D!”

Freeze the algorithm right after $C$ has been expanded. The state of the world is:

  • Explored: $\{S, A, C\}$
  • Frontier: $\{\;\texttt{S-B}: 4,\;\; \texttt{S-A-C-D}: 7\;\}$

UCS pops the minimum, which is S-B at $4$. It expands $B$. $B$'s only child is $D$, reached with

$$g = g(\texttt{S-B}) + c(B, \text{go}, D) = 4 + 1 = 5.$$

Now run the pseudocode's last two lines against this child:

  1. “if the child state is not already in the frontier or explored set” — $D$ is already in the frontier (as S-A-C-D with $g = 7$). So we do not simply add it.
  2. “else if the child is already in the frontier with higher $g(n)$, replace that frontier node with child” — the frontier's entry has $g = 7$, our new child has $g = 5$, and $5 < 7$. So we throw away the old node entirely and put the new one in its place.

After the replacement the frontier holds exactly one node for state $D$: S-B-D with $g = 5$. The node S-A-C-D no longer exists anywhere. That is why the slide writes S-B-D: 5 on the line below S-A-C-D: 7 and annotates it “Replaced by better path to D!”.

Key idea — one node per state on the frontier

In graph search, a state gets at most one frontier node at a time, and that node always carries the cheapest path found so far to the state. Rediscovering the state either upgrades that node (new $g$ smaller) or is discarded (new $g$ larger or equal). The upgrade also rewrites the node's parent pointer — which is how the final answer comes out as $S\!-\!B\!-\!D\!-\!G$ and not $S\!-\!A\!-\!C\!-\!D\!-\!G$.

Common mistake — three of them, actually
  1. Keeping both. Writing a frontier with S-A-C-D: 7 and S-B-D: 5 on it. You then expand $D$ twice and the trace never matches the answer key. One state, one frontier node.
  2. Discarding the new node because “$D$ is already there.” That is the rule for BFS and DFS, where all that matters is reaching a state. For UCS, how expensively you reached it matters, so you must compare.
  3. Forgetting to update the parent pointer. Students update the number 7 → 5 but leave the path reading S-A-C-D, then report the final answer as $S\!-\!A\!-\!C\!-\!D\!-\!G$ with cost 8 — a path that costs 10 and an answer that is internally inconsistent.

Why is the replacement safe — why can't the discarded 7-path have been the right one? Because $D$'s future cost is independent of how we got to $D$. The remaining journey from $D$ to the goal costs whatever it costs; the only thing that differs between the two nodes is the prefix, and $5 < 7$. Any completion of the expensive prefix is beaten, edge for edge, by the same completion of the cheap one. This “the past doesn't constrain the future” property is the optimal substructure that makes the whole method work — and it fails the moment costs depend on history (e.g. a toll that is charged only if you passed through $C$), which is your cue that the offending history belongs in the state.

One more thing to notice about the final answer: $S\!-\!B\!-\!D\!-\!G$ costs $8$, while the path through $C$ costs $1{+}2{+}4{+}3 = 10$. But $S\!-\!A$ is the cheapest first move. UCS did briefly prefer it — it popped $A$ before $B$ — and then the arithmetic overturned it. Greedy first steps are not optimal plans, which is the single most useful sentence on this page.

11. Cost contours: how UCS really spreads

The slide's summary of UCS is one line — “UCS explores increasing cost contours” — next to a picture of concentric rings labelled $c_1, c_2, c_3$ with the Start at the centre and the Goal off to one side. Here is what that picture means.

Define the contour at cost $c$ as the set of states whose cheapest path from the start costs at most $c$. Because UCS always pops the minimum $g$, and because $g$-values of popped nodes never decrease (proved in §13), UCS expands states in non-decreasing order of their optimal cost. So at any moment, the explored set is a contour: a solid blob of everything cheaper than the current frontier minimum.

Figure 4 · UCS expands in rings of equal cost — in every direction at once
What to notice: teal dots are states UCS expands; grey dots are states it never touches. Everything inside the dashed ring — every state reachable for less than $C^*$, in every direction, including straight backwards away from the goal — is expanded before the goal is popped. The wasted work is the entire teal area that isn't on the dashed line. On the next page, a heuristic squashes these circles into ellipses pointing at the goal.

This contour view also explains the complexity bound $O(b^{1+\lfloor C^*/\varepsilon\rfloor})$ from §8: the number of expansions is the number of states inside the $C^*$ contour, and with a minimum step cost $\varepsilon$ you can only be $C^*/\varepsilon$ steps deep inside it.

Plain DFS is rejected because it returns a non-optimal path and may not terminate at all if the space has cycles and you use tree search.

13. Why UCS is complete and optimal — the proof

The slides assert “The good: UCS is complete and optimal!” and move on. Here is the actual argument. Assume every step cost satisfies $c(s,a,s') \ge \varepsilon > 0$.

Lemma 1 — popped costs never decrease

Claim. If UCS pops node $n_1$ and then later pops $n_2$, then $g(n_1) \le g(n_2)$.

Proof. When $n_1$ is popped it is the minimum of the frontier, so every node then on the frontier has $g \ge g(n_1)$. The only nodes ever added afterwards are children of expanded nodes, and a child's cost is $g(\text{parent}) + c \ge g(\text{parent}) \ge g(n_1)$, using $c \ge 0$ and the fact that every subsequently expanded parent was itself popped at or after $n_1$. Replacement only ever lowers a frontier node's $g$ — but never below the cost of the path that produced it, which by the same argument is $\ge g(n_1)$. Hence every node popped after $n_1$ has $g \ge g(n_1)$. $\blacksquare$

This is exactly where non-negative costs are essential. With a negative edge, expanding a node could produce a child cheaper than the node just popped, and the “rings” would no longer be nested — which is why Dijkstra's algorithm (UCS by another name) fails on negative weights and you need Bellman–Ford.

Theorem — when UCS pops a node, its $g$ is optimal for that state

Claim. At the moment UCS pops a node $n$ with state $s$, $g(n)$ equals the cost of a cheapest path from the start to $s$.

Proof (by contradiction). Suppose some cheaper path $P^*$ to $s$ exists, with total cost $g^* < g(n)$.

Walk along $P^*$ from the start and let $u$ be the first state on it that is not in the explored set at this moment. Such a $u$ exists, because $s$ itself is not yet explored (we are popping it right now).

Case A: $u$ is the start state. Then the start was never expanded, which is impossible unless $n$ is the start node itself, in which case $g(n) = 0$ and nothing can be cheaper.

Case B: $u$ has a predecessor $u'$ on $P^*$, and by the choice of $u$, $u'$ is explored. So $u'$ was expanded at some earlier iteration, and at that moment $u$ was generated as a child with cost

$$g(u) \;\le\; \text{cost of the prefix of } P^* \text{ up to } u.$$

(“$\le$” and not “$=$”, because $u'$ might itself have been reached by an even cheaper route, and because a later replacement can only lower $g(u)$ further.) Therefore $u$ is on the frontier right now with

$$g(u) \;\le\; \text{prefix cost} \;\le\; g^* \;<\; g(n),$$

where the middle inequality holds because the remaining suffix of $P^*$ has non-negative cost.

But that contradicts the fact that $n$ was popped as the frontier's minimum: $u$ was sitting right there with a strictly smaller key. Hence no cheaper path exists and $g(n)$ is optimal. $\blacksquare$

Two corollaries you should be able to state

Optimality. The first goal node UCS pops has optimal $g$ by the theorem, and by Lemma 1 nothing popped later could be cheaper. So the returned plan is a cheapest plan. Note how this uses goal-test-on-pop: if we returned on generation, the theorem would not apply, because a generated node's $g$ need not be optimal yet.

Safety of the explored set. Since a state's $g$ is already optimal when it is popped, rediscovering that state later can never yield an improvement — which is precisely why the pseudocode is allowed to ignore children that are already in the explored set. This step is what breaks for A* with a merely admissible (non-consistent) heuristic, which is the subject of the next chapter.

Completeness

Suppose a solution of finite cost $C^*$ exists. Every expansion pops a node with $g \ge$ the previous pop's $g$ (Lemma 1), and any path of $k$ steps costs at least $k\varepsilon$, so only finitely many nodes have $g \le C^*$ — at most the states within depth $\lfloor C^*/\varepsilon \rfloor$. UCS can therefore perform only finitely many pops with $g \le C^*$, and it cannot pop anything with $g > C^*$ while the goal's node (with key $\le C^*$) is on the frontier. Hence the goal is popped within finitely many steps. $\blacksquare$

If $\varepsilon = 0$ is allowed, the argument collapses: infinitely many nodes can share cost 0, and UCS can spin forever inside a zero-cost loop without ever raising the contour.

14. What's wrong with UCS — and what fixes it

The slides end the uninformed-search section with a two-item complaint list. Both items are visible in Figure 4:

  • It explores options in every “direction.” The contours are circles centred on the start. UCS spends just as much effort walking away from the goal as towards it, because $g$ is blind to where the goal is.
  • It has no information about goal location. Nothing in $\text{Actions}$, $\text{Result}$ or $c$ tells UCS which way the goal lies. It is, quite literally, searching with its eyes shut — the definition of an uninformed (blind) search.
Intuition

You want donuts as fast as possible. UCS is the strategy “walk one minute in every possible direction, then two minutes in every possible direction, …” until you trip over a donut shop. It will find the nearest one, and it will have walked most of the city to do it. What you actually do is glance at a map and walk roughly towards the shop, adjusting as you go. That glance — a cheap estimate of remaining distance — is a heuristic.

The fix is to add a second number to the priority. Keep $g(n)$, the backward cost you have already paid, and add $h(n)$, an estimate of the forward cost still to pay. Order the frontier by $h$ alone and you get greedy best-first search (fast, not optimal). Order by $f(n) = g(n) + h(n)$ and you get A*: the contours stop being circles and stretch into ellipses aimed at the goal, while optimality survives as long as $h$ never overestimates.

Where this is going

UCS is A* with $h \equiv 0$. Everything you just learned — the frontier, the explored set, the replacement rule, goal-test-on-pop, the contour argument, even the structure of the optimality proof — carries over unchanged. The only edit is the priority. Continue with Chapter 2: Heuristics, Greedy search and A*.

15. Recap and self-check

  1. A search problem is a state space, $\text{Actions}(s)$, $\text{Result}(s,a)$, $c(s,a,s')$, a start state and a goal test. A solution is a plan: a sequence of actions.
  2. Abstraction — keeping only the variables the problem reads — is what turns $120 \cdot 2^{30} \cdot 12^2 \cdot 4$ into $120$.
  3. A state space graph holds each state once; a search tree holds one node per path, and is infinite whenever the graph has a cycle.
  4. Every algorithm here is the same loop; only the frontier discipline changes: FIFO ⇒ BFS, LIFO ⇒ DFS, priority-by-$g$ ⇒ UCS, priority-by-$g+h$ ⇒ A*.
  5. A node stores state, parent, action, path-cost, with $g(\text{child}) = g(\text{parent}) + c$; the plan is recovered by following parent pointers back.
  6. In UCS, a state keeps one frontier node, which is replaced when a cheaper path to it appears, and the goal test happens on pop.
  7. UCS is complete (given $\varepsilon > 0$) and optimal, in $O(b^{1+\lfloor C^*/\varepsilon\rfloor})$ time and space, and it expands states in cost contours — in all directions, blindly.
