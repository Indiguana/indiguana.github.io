Constraint Satisfaction Problems

After this page you can model a problem as a CSP, run backtracking search by hand, filter with forward checking and AC-3, and explain exactly why MRV and LCV pull in opposite directions.

1. Planning problems vs. identification problems

Every search problem you have met so far — BFS, DFS, UCS and A* — was a planning problem. You were not really asked "what is the goal?" You already knew the goal: get the taxi to Bucharest, get the 8-puzzle into the sorted configuration. What you were asked was how to get there. The answer you hand in is a sequence of actions.

That single fact drives everything in the first three chapters. Because the answer is a path:

  • paths have costs, so it matters which path you return — there is a best one;
  • paths have different depths, so a shallow goal is cheaper to reach than a deep one, which is exactly why BFS is complete and DFS is not;
  • heuristics are useful, because a heuristic $h(n)$ estimates the remaining distance — a quantity that only makes sense when distance is the thing you are optimizing.

CSPs are the other kind of problem. In an identification problem the answer is an assignment of values to variables, and nobody cares how you found it.

Key idea

Planning: the path to the goal is the important thing. Paths have various costs and depths; heuristics give problem-specific guidance.

Identification: the goal itself is the important thing, not the path. Under the standard formulation, every solution sits at exactly the same depth.

CSPs are (mostly) identification problems, and they get their own specialised algorithms because of it.

Analogy

Planning is driving: the route is the deliverable, and a shorter route is a better answer.

Identification is filling in a crossword. There is no "route" to a completed crossword. If you write 3-Down before 1-Across, or the other way round, you end up holding the identical grid. The grid is the answer; the order in which you wrote the letters is not part of it and nobody grades it.

Where the analogy bends: in a crossword you can erase letters, and "erasing" is exactly what backtracking does — so the analogy is honest even about the search process.

Read the three bullets again and notice what each one costs us once we move to identification:

Because every solution is at depth $n$, a heuristic that says "you're getting closer" tells us nothing — we are always exactly $n - |\text{assigned}|$ steps from a complete assignment, on every branch. The guidance that does help is structural: which variable to commit to next, which value to try first, and which parts of the tree are already dead.

Intuition

In planning you ask "am I close?". In identification you ask "am I doomed?". Chapters 1–3 are about the first question. This chapter is about the second — every algorithm below is a device for discovering that you are doomed as early as possible, so you can stop digging.

2. What exactly is a CSP?

A CSP is a search problem with two extra restrictions bolted on. In a standard search problem you are allowed to be completely unstructured:

  • a state is an arbitrary data structure (a board, a city, a tuple of jug volumes);
  • a goal test is any function over states — any code at all that returns true or false.

That generality is why generic search algorithms can do nothing clever: they cannot look inside a state, and they cannot look inside the goal test. A CSP gives up that generality on purpose, and gets algorithms in exchange.

Definition

A constraint satisfaction problem is a triple $(X, D, C)$:

  • Variables $X = \{X_1, X_2, \dots, X_n\}$. A state is an assignment of values to these variables. $n$ is the number of variables.
  • Domains $D$: the set of values a variable may take. Often one shared domain $D$ of size $d$, but in general each variable has its own domain $D_i$ — the course writes "sometimes $D$ depends on $i$". We write $D_i$ for the values still available to $X_i$.
  • Constraints $C$: the goal test, but written as a set of constraints, where each constraint specifies the allowable combinations of values for some subset of the variables.

A solution is a complete assignment (every variable has a value) that is consistent (every constraint is satisfied).

The clause that does all the work is "for subsets of the variables". A general goal test is a black box over the whole state: you must fill in every variable before you may call it. A constraint mentions only two or three variables, so it can be evaluated on a partial assignment the instant those few variables are filled. That is what lets us detect failure early, and early failure detection is the entire performance story of this chapter.

Key idea

Standard search: state = arbitrary data structure, goal test = arbitrary function over states.

CSP: state = assignment to variables $X_i$ with values from a domain $D$ (possibly $D_i$ per variable), goal test = a set of constraints over subsets of the variables. The structure in the goal test is not a limitation — it is the information the algorithms exploit.

3. Why bother? Where CSPs show up

The reason this formalism earns a lecture is that an enormous number of real problems are, once you squint, "assign values to variables so that a pile of local rules all hold". The course lists:

Assignment & timetabling

Assignment problems: who teaches what class. Variables = courses, domain = faculty, constraints = nobody teaches two things at once, everybody is qualified, nobody exceeds their load.

Timetabling: which class is offered when and where. Variables = courses, domain = (time slot, room) pairs, constraints = no room double-booked, required courses not in conflict, room big enough.

Engineering & industry

Hardware configuration: pick components so every interface, power budget and form factor is compatible.

Transportation scheduling and factory scheduling: variables are the start times of jobs, constraints say job B cannot start before job A ends and two jobs cannot use the same machine at once.

Circuit layout: place and route components without overlaps or crossings.

Fault diagnosis: variables are "is component $i$ broken?", constraints are the observed symptoms.

…and many more. Note also that real instances sometimes involve real-valued variables (a start time is a real number, not a colour), which we will come back to in §8.

Example

Sanity check that a familiar problem fits: Sudoku is an assignment problem (which digit goes in each square), not a planning problem (nobody asks for the order in which you filled the squares). It is therefore an identification problem, and every solution is at depth "number of blank squares". We formalise it in §7.

4. The running example: colouring Australia

The whole lecture runs on one instance, so it is worth setting up carefully. We must colour the seven regions of Australia so that no two regions sharing a border get the same colour, using only three colours.

Definition

Variables: $\text{WA},\ \text{NT},\ \text{Q},\ \text{NSW},\ \text{V},\ \text{SA},\ \text{T}$ — Western Australia, Northern Territory, Queensland, New South Wales, Victoria, South Australia, Tasmania. So $n = 7$.

Domains: $D_i = \{\text{red},\ \text{green},\ \text{blue}\}$ for every $i$, so $d = 3$.

Constraints: adjacent regions must have different colours. Written implicitly this is one inequality per shared border, e.g. $\text{WA} \neq \text{NT}$; written explicitly it is a list of allowed pairs, e.g. $(\text{WA}, \text{NT}) \in \{(\text{red},\text{green}),(\text{red},\text{blue}),(\text{green},\text{red}),\dots\}$ — all six ordered pairs of distinct colours.

Solutions are assignments satisfying all of them, for example $$\{\text{WA}=\text{red},\ \text{NT}=\text{green},\ \text{SA}=\text{blue},\ \text{Q}=\text{red},\ \text{NSW}=\text{green},\ \text{V}=\text{red},\ \text{T}=\text{green}\}.$$

5. Constraint graphs

The right-hand picture above is a constraint graph, and it is the data structure the general-purpose algorithms actually operate on.

Definition

A CSP is binary if each constraint relates at most two variables.

For a binary CSP, the binary constraint graph has one node per variable and one edge (arc) per constraint: an edge between $X$ and $Y$ means "there is a constraint restricting which pairs $(x,y)$ are allowed".

Note what the graph deliberately throws away: it records that WA and NT are constrained, not how. That abstraction is the point. An algorithm written against the graph works for map colouring, for scheduling, for n-queens — anything binary — because it never needs to know the semantics of the constraint, only its scope.

General-purpose CSP algorithms use graph structure to speed up search. Three examples, in increasing order of cleverness:

  1. Connected components. Tasmania is an isolated node, so it is an independent subproblem: colouring T has no effect on anything else and vice versa. Solving two components of sizes $n_1$ and $n_2$ separately costs $O(d^{n_1}) + O(d^{n_2})$ instead of $O(d^{n_1 + n_2})$. For Australia that is $3^6 + 3^1 = 732$ instead of $3^7 = 2187$.
  2. Degree. A high-degree node (SA, degree 5) constrains many neighbours, so assigning it early prunes a lot — this is the "degree heuristic", MRV's tie-breaker.
  3. Global shape. If the constraint graph is a tree, the CSP can be solved in $O(n d^2)$ with no backtracking at all. beyond syllabus See §18.
Common mistake

The constraint graph is not the search tree. The graph has 7 nodes and never changes during the search. The search tree has thousands of nodes and is built and destroyed as the algorithm runs. Confusing them is the most common source of "wait, which thing has depth $n$?" — the search tree has depth $n$; the graph has no depth.

Which of these makes a CSP not binary?
Why: "binary" refers to the arity of the constraints — how many variables a single constraint mentions — not to domain size and not to the number of variables. A 9-way alldiff mentions nine variables, so it is a higher-order constraint. (Domain size is $d$; it has nothing to do with arity.)

6. N-queens, modelled twice

The lecture puts up two formulations of n-queens and leaves both of them blank. That blank is the single most useful exercise in the chapter, because it shows that modelling choices are algorithmic choices. The same puzzle, written down two ways, differs by a factor of $10^{12}$ in search-space size before any clever algorithm is applied.

The puzzle: place $n$ queens on an $n \times n$ chessboard so that no two attack each other. Two queens attack each other if they share a row, a column, or a diagonal.

Formulation 1 — one Boolean per square

Definition

Variables: $X_{ij}$ for $i, j \in \{1,\dots,n\}$ — one variable per square of the board. $i$ is the column, $j$ is the row. There are $n^2$ variables.

Domains: $X_{ij} \in \{0, 1\}$, where $1$ means "there is a queen on this square" and $0$ means "empty". So $d = 2$ and this is a Boolean CSP.

Constraints: four families, written out in full below.

Write the constraints explicitly. For every pair of squares that attack each other, we forbid the combination "both are 1". The allowed pairs are therefore $\{(0,0),(0,1),(1,0)\}$ — everything except $(1,1)$:

The fifth does not: the count constraint mentions all $n^2$ variables at once. That is a global constraint, and it is the ugly part of this model.

Common mistake

Forgetting the count constraint. Without it, $X_{ij} = 0$ for every square satisfies every attack constraint — an empty board is a perfectly legal "solution". The attack constraints only say not too many queens; something has to say enough queens. This is a general lesson: a CSP whose constraints are all "forbid" constraints usually has a trivial degenerate solution, and you must add the constraint that rules it out.

Size of the search space. There are $n^2$ variables each with $2$ values, so the number of complete assignments is

$$|{\text{assignments}}| = 2^{n^2}.$$

For $n = 8$ that is $2^{64} \approx 1.845 \times 10^{19}$. If you could test a billion assignments per second you would need about 585 years.

Formulation 2 — one variable per column

Now use a modelling trick that appears everywhere in CSPs: build a constraint into the variables themselves. Exactly one queen goes in each column (if a column had two they would share the column; if some column had none then with $n$ queens in $n$ columns some other column has two). So instead of asking "is there a queen here?", ask "which row holds column $k$'s queen?".

Definition

Variables: $Q_1, Q_2, \dots, Q_n$ — one per column. $n$ variables.

Domains: $Q_k \in \{1, 2, \dots, n\}$, the row index of the queen in column $k$. So $d = n$.

Constraints, implicit form: $$\forall\, i \neq j: \quad Q_i \neq Q_j \quad\text{(no shared row)} \qquad\text{and}\qquad |Q_i - Q_j| \neq |i - j| \quad\text{(no shared diagonal)}.$$

Constraints, explicit form: for each pair $(i,j)$, the list of allowed value-pairs. For $n = 4$, for instance, $$(Q_1, Q_2) \in \{(1,3),\,(1,4),\,(2,4),\,(3,1),\,(4,1),\,(4,2)\}.$$

Take a moment on the diagonal condition, because it is the one people mis-derive. Two queens sit at $(i, Q_i)$ and $(j, Q_j)$ in (column, row) coordinates. They share a diagonal exactly when the horizontal distance equals the vertical distance, i.e. $|i - j| = |Q_i - Q_j|$. Forbidding that gives $|Q_i - Q_j| \neq |i-j|$. Both diagonal directions are covered by the single absolute-value equation, which is why formulation 2 needs one condition where formulation 1 needed two families.

And let us verify that explicit list for $n=4$ by hand, since the course writes it with a "…" and moves on. We need $Q_1 \neq Q_2$ and $|Q_1 - Q_2| \neq |1-2| = 1$ — i.e. the two rows must differ by at least $2$:

For $n = 8$ you would fill $\binom{8}{2} = 28$ tables of $64$ cells each. The implicit form says the same thing in two lines of algebra, which is the practical argument for implicit constraints: they are short to write and cheap to test, and a solver can evaluate $|Q_i - Q_j| \neq |i-j|$ in two instructions instead of searching a stored table.

Key idea

Implicit constraint: a formula or piece of code that returns true/false for a tuple of values. Compact, but opaque — the solver cannot look inside it.

Explicit constraint: an enumerated table of allowed tuples. Bulky, but completely transparent — a solver can index it, intersect it, and precompute supports. Real solvers convert small implicit constraints into explicit tables for exactly that reason.

  2. The CSP becomes purely binary. The $n^2$-ary count constraint is gone, so the constraint graph is a clean $K_n$ (every pair of columns is constrained) and every algorithm in this chapter applies directly.

7. Sudoku as a CSP

Sudoku is the canonical CSP because it is the one the reader has already solved by hand, using — whether they knew it or not — exactly the algorithms in this chapter.

Definition

Variables: each open (blank) square. The given digits are not variables; they are fixed. A typical puzzle has around 50–60 open squares out of 81.

Domains: $\{1,2,\dots,9\}$, so $d = 9$.

Constraints: a 9-way alldiff for each row, each column, and each $3\times 3$ region — 27 constraints in total. ("Region" is the course's word for what puzzle books call a box or block.)

alldiff$(V_1,\dots,V_9)$ is satisfied exactly when all nine values are pairwise distinct. Each such constraint mentions nine variables, so this is a higher-order CSP, not a binary one, and the constraint-graph machinery of §5 does not literally apply.

Decomposing into binary constraints

The course notes the alternative: "or can have a bunch of pairwise inequality constraints". Replace each 9-way alldiff by all $\binom{9}{2} = 36$ pairwise $\neq$ constraints. Then the CSP is binary and every algorithm below runs unmodified.

How many pairwise constraints is that? Naively $27 \times 36 = 972$, but that double-counts: two squares in the same row and the same region generate the same $\neq$ constraint twice. Count instead by squares. Every square has $8$ row-peers, $8$ column-peers, and $8$ region-peers, of which $4$ are already row- or column-peers — so $8 + 8 + 4 = 20$ distinct peers. Total distinct constraints:

$$\frac{81 \times 20}{2} = 810.$$

(Divide by two because each constraint is shared by the two squares it relates.) So the binary Sudoku has $810$ edges over $81$ nodes — a dense but perfectly ordinary constraint graph.

Key idea — the higher-order/binary tradeoff

Higher-order form (27 alldiffs): fewer, larger constraints. Each one can be propagated by a specialised, strong algorithm that sees all nine variables at once.

Binary form (810 inequalities): more, smaller constraints. Generic algorithms (AC-3, forward checking) apply immediately, but propagation is weaker: nine pairwise views of a constraint can miss what the 9-way view catches.

Every higher-order constraint over finite domains can be converted to binary constraints (add auxiliary variables if necessary), so generality is never lost. What is lost is inference strength.

Example — where the binary decomposition is blind

Suppose that after some filtering, three squares in one row have domains

$$D_A = \{1,2\}, \qquad D_B = \{1,2\}, \qquad D_C = \{1,2\}.$$

Under the binary reading, every constraint is satisfiable pairwise: $A=1, B=2$ works; $A=1, C=2$ works; $B=1, C=2$ works. Every arc is consistent (see §13), so filtering reports "no problem" and search continues.

Under the 9-way alldiff reading, three variables need three distinct values but only two values exist between them. By the pigeonhole principle the puzzle is already dead. A dedicated alldiff propagator (Régin's algorithm, via bipartite matching) detects exactly this and fails immediately. beyond syllabus The general phenomenon — that local pairwise consistency misses global infeasibility — is the subject of §15.

A last observation that will matter in §17: when a human solves Sudoku, the move "this square can only be a 7, so write 7" is precisely minimum remaining values — choosing the variable whose domain has shrunk to size one. And "cross 7 off every peer of this square" is precisely forward checking. You already run these algorithms; this chapter just names them.

8. Varieties of CSPs

Everything so far assumed finite domains of colours or row indices. The formalism is wider than that, and it is worth knowing which parts of it today's algorithms cover.

Discrete variables, finite domains

This is our case. With $n$ variables and domain size $d$, the number of complete assignments is

$$d^n,$$

so brute-force enumeration is $O(d^n)$ — exponential in the number of variables, and it is exponential no matter how clever we are, because:

Definition

A Boolean CSP is a finite-domain CSP with $d = 2$. The most famous one is Boolean satisfiability (SAT): variables are propositional atoms with domain $\{\text{true},\text{false}\}$, and each constraint is a clause such as $(x_1 \vee \neg x_2 \vee x_3)$, which forbids exactly one of the eight assignments to those three variables.

SAT is NP-complete (Cook–Levin, 1971). Since SAT is a special case of finite-domain CSP, deciding whether a CSP has a solution is NP-hard in general.

Read that consequence carefully, because it sets expectations for the rest of the chapter. No algorithm below changes the worst-case complexity. Forward checking, AC-3, MRV and LCV are all heuristics and pruning rules: they shrink the tree enormously on realistic instances, and they change nothing at all in the worst case. That is not a failure — it is the only honest thing an exponential-hard problem allows.

Discrete variables, infinite domains

Domains may be infinite but still discrete: the integers, or the set of all strings.

The course's example is job scheduling, where the variables are the start and end times of each job. If jobs can start at any integer minute, the domain is $\mathbb{Z}$ and you cannot enumerate it. You therefore cannot write constraints as explicit tables of allowed tuples — an infinite table is not a data structure. You need a constraint language instead, and you write things like

$$\text{Start}_{J_1} + 5 \le \text{Start}_{J_3},$$

meaning "job $J_1$ takes five minutes and $J_3$ cannot begin until it is finished".

  • Linear constraints over integers (sums of variables with integer coefficients, compared by $\le$, $=$, $\ge$) are solvable — decidable, by integer programming methods.
  • Nonlinear integer constraints are undecidable: there is no algorithm that decides, for every such system, whether a solution exists. This is Matiyasevich's 1970 theorem resolving Hilbert's tenth problem about Diophantine equations. beyond syllabus "Undecidable" is much stronger than "slow": it is not that we lack a fast algorithm, it is that no algorithm exists.

Continuous variables

The course's example is scheduling Hubble Space Telescope observations: the start and end times of each observation are real numbers, subject to constraints such as "this observation must finish before Earth occults the target" and "the slew between these two targets takes at least 12 minutes".

Here the news is unexpectedly good: with linear constraints on continuous variables, feasibility is solvable in polynomial time — this is linear programming, and it is one of the genuinely tractable corners of optimisation.

Out of scope

The slides mark continuous CSPs "we will cover in 07-380". Linear and convex optimisation is a different course; do not expect it on this exam. Note only the shape of the landscape: continuous + linear is polynomial, discrete + finite is NP-hard, and discrete + infinite + nonlinear is undecidable. Discreteness, not size, is what makes CSPs hard.

9. Varieties of constraints

Constraints vary along a second axis: how many variables one constraint mentions — its arity.

Unary constraints

A unary constraint mentions a single variable: "South Australia dislikes green", $\text{SA} \neq \text{green}$.

Intuition

Unary constraints are free. A constraint on one variable is simply a statement about which values that variable may take — which is what a domain is. So you delete the forbidden values from the domain once, before search starts, and then forget the constraint ever existed. In the course's words, unary constraints are "equivalent to reducing domains". No algorithm in this chapter needs to handle them at run time.

Worked instance: $D_{\text{SA}} = \{\text{red},\text{green},\text{blue}\}$ with the unary constraint $\text{SA} \neq \text{green}$ becomes $D_{\text{SA}} = \{\text{red},\text{blue}\}$, and the constraint set drops that constraint. Done in $O(d)$, once, forever.

Binary constraints

A binary constraint mentions exactly two variables: $\text{SA} \neq \text{NSW}$. This is the focus of the whole lecture, because binary constraints are exactly the ones that give a constraint graph, and a graph is a thing algorithms can walk.

Higher-order constraints

Three or more variables: the Sudoku alldiff of §7, or the column constraints of a cryptarithmetic puzzle (TWO + TWO = FOUR, where one column relates two digits, a carry in and a carry out — four variables at once).

A higher-order constraint over $k$ variables corresponds to a hyperedge joining $k$ nodes, giving a constraint hypergraph rather than a graph. The standard move, as in §7, is to decompose into binary constraints so the binary machinery applies.

Soft constraints (preferences)

Everything so far is hard: an assignment either satisfies the constraints or it is not a solution. Real problems also have preferences — the course's example is "red is better than green".

Definition

A soft constraint or preference is often represented by attaching a cost to each variable assignment. The cost of a complete assignment is the sum of the costs of its parts, and we seek the cheapest assignment that satisfies all the hard constraints:

$$\text{minimise} \quad \sum_{i=1}^{n} \text{cost}_i(X_i = v_i) \quad\text{subject to all hard constraints being satisfied.}$$

This turns a satisfaction problem into a constrained optimisation problem.

Common mistake

Thinking preferences are a small extension. They are not: they break the defining property of identification problems from §1. Once assignments have costs, the first solution you find is no longer good enough — you must keep searching to prove no cheaper one exists, or use branch-and-bound. Every algorithm below stops at the first solution, and that is only correct because all solutions are equally good.

A quick example to make the arithmetic concrete. Suppose in Australia every region costs $0$ for red, $1$ for green and $3$ for blue. The solution from §4 — WA red, NT green, SA blue, Q red, NSW green, V red, T green — costs $0+1+3+0+1+0+1 = 6$. Recolouring T from green to red is still legal (T has no neighbours) and costs $5$. So that solution was not optimal, even though it was perfectly valid. Under hard constraints only, both are equally correct answers; under preferences, only one is.

10. A CSP is a search problem

Before inventing anything new, let us check that the search machinery of Chapter 2 already applies. It does, verbatim.

Definition — standard search formulation of a CSP
  • States are the values assigned so far, i.e. partial assignments such as $\{\text{WA}=\text{red},\ \text{NT}=\text{green}\}$.
  • Initial state: the empty assignment, $\{\}$.
  • Successor function: assign a value to an unassigned variable — and, in the naive version, it may be any unassigned variable, with any value from its domain.
  • Goal test: the current assignment is complete (every variable has a value) and satisfies all constraints.

Three consequences follow immediately and they are worth stating out loud:

  1. Solutions appear only at depth $n$, because each successor step assigns exactly one variable and the goal test demands all $n$.
  2. The tree has no infinite paths and no cycles: every step strictly increases the number of assigned variables, so the deepest any path can go is $n$.
  3. The branching factor is $(n-\ell)\,d$ at depth $\ell$: any of the $n - \ell$ still-unassigned variables, times any of its $d$ values.

That third point is a disaster. Multiply the branching factors down the tree:

$$\#\text{leaves} \;=\; (n d)\big((n-1)d\big)\cdots(1\cdot d) \;=\; n!\, d^{\,n}.$$

For Australia, $n = 7$, $d = 3$:

$$7! \cdot 3^7 = 5040 \times 2187 = 11{,}022{,}480 \ \text{leaves},$$

while there are only $3^7 = 2187$ distinct complete assignments. Every assignment is reached $5040$ times, once per ordering of the seven variables. We are doing five thousand times more work than the problem contains. Fixing that is Idea 1 of §11.

The naive algorithm: DFS with the goal test at the bottom

The course's starting point is deliberately dumb, and worth running once so you feel the pain:

  • At each node, assign a value from the domain to a variable.
  • Check feasibility (the constraints) only when the assignment is complete.

This treats the goal test as the black box of general search: you may not call it until every variable has a value. So we build $\text{WA}=\text{red},\ \text{NT}=\text{red}$ — already illegal, they share a border — and cheerfully extend it through five more variables, generating $3^5 = 243$ complete assignments underneath a prefix that was dead on arrival, and rejecting all $243$ one at a time.

Intuition

This is like filling in a crossword entirely at random, checking nothing, then at the very end reading the whole grid to see if it happens to be right. You know instantly that the right move is to check each word as you write it. That instinct is exactly "backtracking search", and the fact that it is obvious to you is the point: the algorithm is not clever, it is just refusing to be stupid.

Poll 1 — should we use BFS or DFS?

Answer: DFS — and it is not close.

1. BFS's advantage is unavailable. BFS is preferred when it matters that you find the shallowest goal, because shallowest means cheapest when every step costs the same. Here every solution sits at exactly depth $n$ (§1). There is no shallow solution to find, so BFS's optimality guarantee buys literally nothing.

2. DFS's disadvantage is unavailable too. DFS is normally incomplete because it can dive down an infinite path and never return. The CSP tree has depth exactly $n$ — every path terminates after $n$ assignments. So DFS is complete here, for free.

3. Memory. This is the decisive argument. BFS must hold an entire level of the frontier: expanding level $n-1$ means storing on the order of $d^{\,n}$ nodes (for Australia, at least $2187$ partial assignments, and $11$ million if you count the duplicated orderings). DFS stores one root-to-leaf path: $O(n)$ nodes, or $O(nd)$ if you also remember which values remain to try at each level. For Australia that is 7 nodes versus thousands, and the gap is exponential in $n$.

4. Time to first solution. BFS would generate every partial assignment of size $1$, then every one of size $2$, and so on — it reaches its first complete assignment only after enumerating all the incomplete ones. DFS reaches a complete assignment after $n$ expansions. Since any solution is as good as any other, getting to the bottom fast is exactly what we want.

So: depth-first search, and everything below is DFS with improvements bolted on.

Why is DFS complete for a CSP even though DFS is incomplete for search problems in general?
Why: DFS fails to be complete only when it can descend forever. Here the state is a partial assignment and every step strictly grows it, so after $n$ steps there is nothing left to assign. A finite tree makes DFS complete. Option A confuses the constraint graph with the search tree (see the warning in §5) — the constraint graph is full of cycles, and it does not matter.

11. Backtracking search

Key idea

Backtracking search is the basic uninformed algorithm for solving CSPs, and $$\textbf{backtracking search} \;=\; \textbf{DFS} \;+\; \textbf{two improvements}.$$

Idea 1 — one variable at a time

Variable assignments are commutative:

$$[\,\text{WA}=\text{red} \text{ then } \text{NT}=\text{green}\,] \quad\text{is the same state as}\quad [\,\text{NT}=\text{green} \text{ then } \text{WA}=\text{red}\,].$$

Both are the set $\{\text{WA}=\text{red},\ \text{NT}=\text{green}\}$. A set has no order. So a search that explores both orderings explores the same state twice, and in general explores each state $\ell!$ times at depth $\ell$.

The fix is a single line of code: at each node, fix one variable and branch only on its values. Which variable you pick is up to you; what matters is that you pick one and do not consider the others at this node.

Why this is sound

It looks like we are throwing away options — at the root we now generate $3$ children instead of $21$. Could we lose a solution?

No. Let $S$ be any solution, a complete assignment. Suppose at the root we commit to branching on $\text{WA}$. $S$ gives $\text{WA}$ some value $v$, so $S$ lies in the subtree under the child $\text{WA}=v$ — that child exists, because we generate a child for every value in $D_{\text{WA}}$. Recurse: at every node, whichever variable we choose to branch on, $S$ assigns it some value, and that branch exists. By induction $S$ is reachable.

What we discarded were alternative orderings of the same assignments, never alternative assignments. Completeness is preserved exactly. (Note the proof also shows that any variable-selection rule is sound — which is what licenses MRV in §17.)

Quantifying the saving. Branching factor drops from $nd$ to $d$; the leaf count drops from $n!\,d^{\,n}$ to $d^{\,n}$; that is a factor of $n!$.

Idea 2 — check constraints as you go

Consider only values which do not conflict with previous assignments. This may need some computation to check the constraints — for each candidate value you must test it against the already-assigned neighbours — but that cost is trivial compared to the subtree you avoid. The course calls this the incremental goal test: rather than one big test at depth $n$, a small test at every node.

Concretely, in Australia with $\text{WA}=\text{red}$ already assigned, when we come to $\text{NT}$ we simply never generate the child $\text{NT}=\text{red}$. The naive DFS would have generated it and then built all $3^5 = 243$ complete assignments below it before noticing.

The algorithm in full

function BACKTRACKING-SEARCH(csp) returns a solution, or failure
    return RECURSIVE-BACKTRACKING({}, csp)


function RECURSIVE-BACKTRACKING(assignment, csp) returns a solution, or failure

    if assignment is complete then
        return assignment                          # every variable has a value, and
                                                   # every value was checked on the way in

    var  <- SELECT-UNASSIGNED-VARIABLE(VARIABLES[csp], assignment, csp)     # decision point 1

    for each value in ORDER-DOMAIN-VALUES(var, assignment, csp) do          # decision point 2

        if value is consistent with assignment given CONSTRAINTS[csp] then  # decision point 3
            add {var = value} to assignment
            result <- RECURSIVE-BACKTRACKING(assignment, csp)
            if result != failure then
                return result
            remove {var = value} from assignment   # <- this line is the "backtrack"

    return failure                                 # no value for var works; tell the caller

Every line earns its place, so read them one at a time.

  • if assignment is complete then return assignment — note there is no constraint check here. We do not need one: every value was checked against the existing assignment at the moment it was added, so a complete assignment is automatically consistent. The course states this explicitly ("no need to check constraints for a complete assignment"), and it is the pay-off of the incremental goal test.
  • SELECT-UNASSIGNED-VARIABLE — returns any unassigned variable. Sound for any choice, by the proof above. Plain backtracking takes the next one in a fixed order; MRV makes this smart.
  • ORDER-DOMAIN-VALUES — returns the values of $D_{var}$ in some order. Sound for any order, since the loop tries them all. LCV makes this smart.
  • if value is consistent with assignment — this is Idea 2, the fail-on-violation test. It checks only the constraints between var and the already assigned variables; constraints involving two unassigned variables are not testable yet.
  • remove {var = value} from assignment — the actual backtrack. We undo the assignment and try the next value. In an implementation that also maintains filtered domains, this line must additionally restore the domains to their pre-assignment state.
  • return failure — reached when the for loop is exhausted: no value of var can work, so this whole subtree is dead and the parent must try something else.
Say it in one line

Backtracking = DFS + variable ordering + fail-on-violation. And the decision points — the three places where a smarter policy can be dropped in without touching correctness — are: (1) which variable next (§17, MRV), (2) which value first (§17, LCV), and (3) how hard to look for trouble at each node (§12 forward checking, §14 AC-3). A fourth, beyond this course, is (4) how far to jump back on failure — plain backtracking undoes one assignment; backjumping undoes several at once. beyond syllabus

With just these two improvements, backtracking search solves n-queens for $n \approx 25$. That is the honest number from the course: not thousands, twenty-five. Holding onto that figure makes the improvements in the rest of the chapter feel necessary rather than decorative — by §17 the same basic algorithm will handle $n = 1000$.

12. Filtering, part 1: forward checking

Backtracking still wastes effort in a specific, diagnosable way. Look at the state $\{\text{WA}=\text{red},\ \text{Q}=\text{green},\ \text{V}=\text{blue}\}$. It is perfectly consistent — no two of WA, Q, V even share a border. Plain backtracking sees nothing wrong and carries on assigning NT, then NSW, then SA. But it is already dead: SA borders all three of WA, Q and V, so SA can be neither red nor green nor blue. Plain backtracking will not discover this until it actually gets to SA, after building every combination of NT and NSW above it.

Key idea — filtering

Filtering: keep track of the domains of the unassigned variables, and cross off bad options as you go. Failure is detected the moment some variable has no values remaining — which can be long before that variable is reached by the search.

Definition — forward checking

The simplest filtering rule. After a variable is assigned a value, check the constraints it participates in and cross off the values of the unassigned variables that violate them. For map colouring: after $X = c$, delete $c$ from the domain of every unassigned neighbour of $X$. If any domain becomes empty, fail and backtrack immediately.

Analogy

Forward checking is the pencil marks in a Sudoku grid. You do not just write a 7 into a square; you immediately rub the little 7 out of every square in that row, column and box. The instant a square has no pencil marks left, you know you went wrong earlier — without having to reach that square in your solving order. Forward checking is the algorithmic version of that habit, and it costs the same as the habit does: a little bookkeeping per move.

13. Consistency of a single arc

Forward checking is a special case of something more general, and naming the general thing lets us strengthen it. The general thing is arc consistency.

Definition

Let $X$ and $Y$ be two variables joined by a constraint, and consider the directed arc $X \to Y$. The arc has a tail ($X$) and a head ($Y$).

The arc $X \to Y$ is consistent iff for every value $x$ in the tail's domain $D_X$, there is some value $y$ in the head's domain $D_Y$ such that the pair $(x,y)$ does not violate the constraint between $X$ and $Y$.

Every symbol, named: $x$ ranges over the values currently left in $D_X$; $y$ ranges over the values currently left in $D_Y$; "does not violate" means the pair is allowed by the constraint (for map colouring, $x \neq y$). A $y$ that works for a given $x$ is called a support for $x$.

So: the arc $X \to Y$ is consistent iff every value in the tail has at least one support in the head.

ENFORCING AN ARC DELETES FROM THE TAIL

To enforce arc consistency on $X \to Y$: remove from $D_X$ every value that has no support in $D_Y$.

The head's domain is not touched. Not shrunk, not grown, not read-and-modified — only read.

The lecture prints "Remember: delete from the tail!" at the bottom of fifteen consecutive slides. That is not decoration; it is the single most common place to go wrong by hand. Arc $X \to Y$ ⟹ values die in $X$.

What to notice: the arrow points at WA, but the damage happens at SA. A useful mnemonic: the arrow is a question the tail asks the head — "given what you can still be, can I still be this?" — and only the asker changes its mind.

Forward checking, re-read as arc consistency

Now the punchline of the section. The course writes forward checking as:

$$\text{enforce } X \to Y \quad\text{for all } (X,Y) \in E \text{ with } Y \text{ newly assigned.}$$

Unpack it. $E$ is the edge set of the constraint graph. $Y$ is the variable we just assigned, so $D_Y$ is a singleton $\{c\}$. $X$ ranges over $Y$'s neighbours. Enforcing $X \to Y$ deletes from $D_X$ every value with no support in $\{c\}$ — and for a $\neq$ constraint the only value without support is $c$ itself. So enforcing those arcs deletes exactly $c$ from each neighbour's domain. That is forward checking, verbatim.

Key idea

Forward checking = enforce arc consistency on the arcs pointing at the newly assigned variable, once.

Full arc consistency = enforce it on every arc, repeatedly, until nothing changes.

Full arc consistency is strictly stronger, in the precise sense that it makes every deletion forward checking makes and possibly more. Two separate reasons, and it is worth keeping them apart:

  1. More arcs. Forward checking only ever examines arcs $X \to Y$ where $Y$ has just been assigned. It never examines an arc between two unassigned variables. Arc consistency examines all of them — which is exactly how it catches "NT and SA are both forced to blue and share a border".
  2. Propagation. When forward checking removes a value from $D_X$, it stops. Arc consistency asks: did shrinking $D_X$ destroy the support of some value in a third variable $W$ that neighbours $X$? If so, that value dies too, which may destroy support elsewhere, and so on. Deletions cascade. Forward checking has no cascade — it is one layer deep.
Why "strictly stronger" is literally true

Claim: let $D^{\text{FC}}$ be the domains after forward checking on assignment of $Y$, and $D^{\text{AC}}$ the domains after enforcing full arc consistency from the same starting point. Then $D^{\text{AC}}_X \subseteq D^{\text{FC}}_X$ for every $X$.

Proof: the arcs forward checking enforces are a subset of the arcs arc consistency enforces, and enforcing an arc only ever removes values. A value removed by enforcing some arc is removed by any procedure that enforces that arc and reaches a fixed point. Hence every value FC removes, AC also removes; AC may additionally remove values via arcs FC never looked at. $\square$

"Strictly": the Australia trace of §14 exhibits a case where AC empties a domain and FC does not, so the inclusion can be proper.

And an immediate corollary that we will cash in shortly: arc consistency detects failure at least as early as forward checking, and sometimes earlier — never later.

You enforce arc consistency on the arc $\text{NSW} \to \text{SA}$, where $D_{\text{NSW}} = \{\text{R},\text{G},\text{B}\}$ and $D_{\text{SA}} = \{\text{B}\}$. What changes?
Why: NSW is the tail, so NSW is where values die. Blue in NSW has no support, because the only value left in the head SA is blue and $\text{B} = \text{B}$ violates the constraint. Red and green both find the support $y = \text{B}$, so they stay. SA is the head and is only read. If you want SA to lose values you must enforce the other arc, $\text{SA} \to \text{NSW}$ — arcs are directed and both directions of every edge must eventually be processed.

14. AC-3: enforcing arc consistency on the whole CSP

Knowing how to enforce one arc, we need a procedure that makes every arc consistent simultaneously. The difficulty is that the arcs interact: enforcing $X \to Y$ shrinks $D_X$, which can break an arc $W \to X$ that was consistent a moment ago. So one pass is not enough.

The simplistic algorithm

The course's first proposal:

repeat
    changed <- false
    for each ordered pair (X, Y) of variables joined by a constraint do
        if enforcing X -> Y removes any value then changed <- true
until changed = false

Cycle over the pairs of variables enforcing arc consistency, repeating the cycle until no domain changes for a whole cycle. It is obviously correct — it stops only at a fixed point, and a fixed point is by definition arc-consistent — and obviously wasteful. One full cycle costs $O(|E| d^2)$ even if the only thing that changed was a single value in a single domain, and you may need many cycles. In the worst case you re-check every arc after every single deletion.

AC-3

Definition

AC-3 (Arc Consistency algorithm #3, Mackworth 1977) is the same idea with a queue of arcs still to check, so that it ignores constraints that have not been modified since they were last analysed. An arc goes back on the queue only when something it depends on has actually changed.

function AC-3(csp, queue) returns false if an inconsistency is found, true otherwise
    # queue defaults to ALL directed arcs (Xi, Xj) of the constraint graph --
    # both directions of every edge

    while queue is not empty do
        (Xi, Xj) <- REMOVE-FIRST(queue)

        if REVISE(csp, Xi, Xj) then                 # Di actually shrank
            if size of Di = 0 then
                return false                        # wipeout: this CSP branch is dead

            for each Xk in NEIGHBORS(Xi) \ {Xj} do
                add (Xk, Xi) to queue               # Di shrank, so everyone who
                                                    # depends on Di must be re-checked
    return true


function REVISE(csp, Xi, Xj) returns true iff we removed something from Di
    revised <- false
    for each x in Di do
        if no value y in Dj satisfies the constraint between Xi and Xj given x then
            delete x from Di                        # DELETE FROM THE TAIL
            revised <- true
    return revised
The enqueue rule — the only subtle line

When a value is deleted from $D_X$, re-enqueue the arc $W \to X$ for every neighbour $W$ of $X$.

Why into $X$ and not out of it? Because $D_X$ is the head of the arcs $W \to X$, and a head's domain is what supplies supports. Shrinking $D_X$ can destroy the support of some value in $D_W$, so every $W$ that leans on $X$ must be re-examined. Arcs out of $X$ ($X \to Z$) are unaffected: a smaller tail cannot create new unsupported values in some other variable.

The lecture's trace enqueues all neighbours $W$ of $X$, including the head $X_j$ we just compared against. The textbook writes $\text{NEIGHBORS}(X_i) \setminus \{X_j\}$, skipping it. Both are correct — see the box below for why skipping is safe — and skipping is simply a small optimisation. We follow the lecture's version in the trace so the queues match the slides exactly.

Why it is safe to skip the arc back to the head

Suppose REVISE$(X_i, X_j)$ deleted the value $x$ from $D_i$. Could that deletion cost some value $y \in D_j$ its support, making the arc $X_j \to X_i$ newly inconsistent?

For that, $y$'s only support in $D_i$ would have to have been $x$ — i.e. $(y, x)$ satisfies the constraint. But $x$ was deleted precisely because no value of $D_j$ supports it: for every $y' \in D_j$, the pair $(x, y')$ violates the constraint. Taking $y' = y$ gives that $(x,y)$ violates the constraint, contradicting $(y,x)$ satisfying it. (For binary constraints the relation is symmetric in this sense: $(x,y)$ allowed iff $(y,x)$ allowed, reading each in the right order.)

So no value of $D_j$ ever depended on a value we deleted from $D_i$, and $X_j \to X_i$ cannot have been broken. $\square$

Where AC-3 fits, and what it costs

  • Arc consistency detects failure earlier than forward checking. Proved in §13 and exhibited above.
  • It can be run as a preprocessor or after each assignment. As a preprocessor it is run once on the raw CSP, before any search; it is cheap and can shrink every domain permanently (and occasionally proves the whole problem infeasible before you begin). After each assignment it is run inside the recursion, seeded with the arcs into the just-assigned variable, and its effects must be undone on backtrack.
Answer — what is the downside of enforcing arc consistency?

Cost. One call to AC-3 is $O(n^2 d^3)$ (derived in §16), and backtracking search calls it at every node. Forward checking, by contrast, costs $O(\text{deg}(X) \cdot d) $ — a handful of deletions. You are buying pruned subtrees with CPU time, and the exchange rate is not always favourable.

Three specific ways the trade can go badly:

  • Loosely constrained problems. If domains are large relative to the constraints, AC-3 sweeps every arc and deletes nothing. You paid $O(n^2d^3)$ for zero information, at every node.
  • Deep search trees. The cost is per node and the tree can have exponentially many nodes, so a constant-factor slowdown per node is a constant-factor slowdown overall — which you only recoup if the pruning actually removes subtrees.
  • Redundant work. Much of what AC-3 recomputes at a node was already computed at the parent. Incremental variants (AC-4, AC-6, AC-2001) keep support counts between calls to avoid this, at the price of memory and bookkeeping. beyond syllabus

There is also a second, subtler downside, and it is the whole of the next section: arc consistency can succeed and still be wrong. An arc-consistent CSP may have no solution at all, so passing the AC-3 test proves nothing.

15. The limitations of arc consistency

AC-3 returning true feels like a certificate. It is not one. After enforcing arc consistency you may be in any of three situations:

Case 1

One solution left. Every domain is a singleton and they are mutually consistent — as in Guided problem 2. Read the answer off the domains; you are done.

Case 2

Many solutions left. Domains have shrunk but several still hold multiple values. You have a smaller CSP, not an answer. Keep searching.

Case 3

No solutions left — and you do not know it. Every arc is consistent, every domain is non-empty, and yet no complete assignment satisfies all constraints. AC-3 reports success on an unsolvable problem.

Case 3 is the one to internalise, and it is what the lecture's "What went wrong here?" slide is pointing at.

Example — arc-consistent with no solution

Three variables $X$, $Y$, $Z$. Domains $D_X = D_Y = D_Z = \{\text{red}, \text{green}\}$. Constraints: $X \neq Y$, $Y \neq Z$, $X \neq Z$ — a triangle.

Every arc is consistent. Check one and the rest follow by symmetry. Arc $X \to Y$: does red in $D_X$ have a support? Yes — green in $D_Y$, and red ≠ green. Does green in $D_X$ have a support? Yes — red in $D_Y$. So nothing is deleted. The same holds for all six directed arcs. AC-3 drains its queue without a single deletion and returns true.

There is no solution. The three variables must take pairwise distinct values, so we need three distinct values; we have two. By the pigeonhole principle, two of $X, Y, Z$ share a value, and those two are constrained to differ. Contradiction. (Equivalently: a triangle is a 3-clique and needs 3 colours; we offered 2.)

What went wrong: nothing went wrong locally. Every pair is individually satisfiable. The contradiction lives in a three-variable interaction, and arc consistency — by construction — only ever looks at two variables at a time.

Three things to remember
  • Arc consistency only checks local consistency conditions — two variables and one constraint at a time.
  • An arc-consistent CSP can still be unsolvable, and AC-3 will not say so. Non-empty domains are necessary, not sufficient.
  • Arc consistency still runs inside a backtracking search. It is a pruning subroutine, never a solver. The search is what actually decides satisfiability; AC-3 just makes it do less work. This is why §14's pseudocode returns "true/false", not "solution".
AC-3 finishes on a CSP with every domain non-empty. What may you conclude?
Why: the triangle above is arc-consistent with non-empty domains and has zero solutions, which kills option A. Option B is also wrong: singleton domains that happen to violate a constraint are possible in general — the reliable statement is only that arc consistency has removed every value that fails a pairwise support test. Any conclusion about solvability must come from the search, not from the filter.

16. The cost of one run of AC-3

The lecture derives the bound in four steps. Each step is one line, and each line is worth pausing on.

Derivation

Step 1 — an arc is enqueued only after a value is removed. Look at the pseudocode: add (Xk, Xi) to queue sits inside if REVISE(...) then, and REVISE returns true only when it actually deleted something. (The one exception is the initial queue, handled in step 3.) So "how many arcs get processed?" reduces to "how many deletions can happen?".

Step 2 — there are at most $O(nd)$ removals in the whole run. There are $n$ variables, each with a domain of at most $d$ values, so there are at most $nd$ values in existence. Every removal destroys one value permanently — AC-3 never puts a value back — so there can be at most $nd$ removals ever. This is the crucial monotonicity argument: domains only shrink, which is what makes the algorithm terminate at all.

Step 3 — each removal enqueues at most $n$ arcs, so $O(n^2 d)$ arc insertions. When a value dies in $D_{X_i}$, we enqueue one arc per neighbour of $X_i$. A variable has fewer than $n$ neighbours (at most $n-1$), so each removal adds $\le n$ arcs. Multiply by the $O(nd)$ removals: $O(n^2 d)$ insertions. The initial queue contributes $2|E| \le n(n-1) = O(n^2)$ arcs, which is dominated by $O(n^2d)$ whenever $d \ge 1$. Each insertion is processed at most once, so the while loop runs $O(n^2d)$ times.

Step 4 — processing one arc costs $O(d^2)$. REVISE$(X_i, X_j)$ loops over the $\le d$ values $x \in D_i$ and, for each, scans the $\le d$ values $y \in D_j$ looking for a support. That is $d \times d$ constraint checks in the worst case, each $O(1)$.

Multiply. $$\underbrace{O(n^2 d)}_{\text{arcs processed}} \times \underbrace{O(d^2)}_{\text{cost per arc}} \;=\; \boxed{O(n^2 d^3)}$$ for a single run of AC-3.

Sanity-check the factors against Australia: $n = 7$, $d = 3$, giving $n^2 d^3 = 49 \times 27 = 1323$ constraint checks as an upper bound for one call. The trace in §14 used about 15 arcs and a few dozen checks — the bound is loose, as worst-case bounds are, but it is the right shape.

A common way to write the same bound

Textbooks often state AC-3 as $O(e\, d^3)$ where $e = |E|$ is the number of edges (constraints) rather than $O(n^2d^3)$. The two agree: a binary constraint graph on $n$ nodes has $e \le \binom{n}{2} = O(n^2)$ edges, and the derivation above used "$\le n$ neighbours" exactly where a finer count would use the degree. For sparse graphs — a road map, a schedule — $e$ is closer to $O(n)$ and AC-3 is much faster than the $n^2$ form suggests.

The tightened bound. beyond syllabus Zhang and Yap (2001) showed that with a smarter pass over the arcs the true worst-case complexity of AC-3 is $O(n^2 d^2)$, saving a factor of $d$: their analysis charges each constraint check to the value whose support pointer advanced, so the $d^2$ scan is not repeated from scratch on every visit to an arc. The lecture marks this "not required". Know that the bound exists and that the classroom answer is $O(n^2d^3)$.

Remember what this cost multiplies

This is the cost of one run. The whole backtracking algorithm with AC-3 calls AC-3 many times — once per node of the search tree, and the tree can have $O(d^n)$ nodes. The total is therefore $O(d^n \cdot n^2 d^3)$ in the worst case, which is worse than plain backtracking's worst case. AC-3 is a bet that the pruning saves more nodes than the filtering costs. On structured problems it wins enormously; on loose ones it loses. See the downside box in §14.

Where do you run AC-3? — the lecture's question, answered

Answer: in two places.

1. Once as a preprocessor, before search starts, with the queue seeded with all directed arcs. This is pure profit: it costs one $O(n^2d^3)$ call and every value it deletes is deleted for the entire search, at every node, forever. If it returns false, the CSP is unsatisfiable and you never search at all.

2. After each assignment, inside the recursion, with the queue seeded only with the arcs $W \to X$ for the neighbours $W$ of the just-assigned variable $X$. Seeding with all arcs would be correct but wasteful: the only domain that just changed is $D_X$ (collapsed to a singleton), so the only arcs that can newly fail are the ones whose head is $X$ — and everything else follows by propagation from there.

function BACKTRACKING-WITH-AC3(csp) returns a solution, or failure
    if AC-3(csp, queue = ALL-ARCS(csp)) = false then
        return failure                                  # preprocessing pass: whole CSP is dead
    return RECURSE({}, csp)


function RECURSE(assignment, csp) returns a solution, or failure
    if assignment is complete then return assignment

    var <- SELECT-UNASSIGNED-VARIABLE(...)              # MRV (see section 17)

    for each value in ORDER-DOMAIN-VALUES(var, ...) do  # LCV (see section 17)

        if value is consistent with assignment then
            add {var = value} to assignment
            saved <- copy of all current domains        # so we can undo the filtering
            D[var] <- {value}

            queue <- { (W, var) : W in NEIGHBORS(var) } # only the arcs into var
            if AC-3(csp, queue) then                    # no domain wiped out
                result <- RECURSE(assignment, csp)
                if result != failure then return result

            restore all domains from saved              # undo filtering, then
            remove {var = value} from assignment        # undo the assignment

    return failure

Two details in that code are easy to get wrong and both are fatal if you do:

  • saved <- copy of all current domains must happen before D[var] <- {value}, and the restore must happen on every exit from the loop body that does not return a solution — including the path where AC-3 returns false.
  • The queue is seeded with arcs pointing at var, i.e. $(W, \textit{var})$ with $W$ the tail. Seeding $(\textit{var}, W)$ instead is the classic direction bug: those arcs are already consistent, the propagation never starts, and your solver silently degenerates into plain backtracking.

17. Ordering: MRV and LCV

Filtering answered "can we detect inevitable failure early?". Ordering answers the other two questions the lecture raises about improving backtracking:

  • Which variable should be assigned next? — the SELECT-UNASSIGNED-VARIABLE hook.
  • In what order should its values be tried? — the ORDER-DOMAIN-VALUES hook.

Both are free in the sense that correctness does not depend on them (the soundness proof in §11 allowed any choice). They are pure speed. And — this is the part students consistently get backwards — the two questions have opposite answers.

Variable ordering: minimum remaining values

Definition

Minimum remaining values (MRV): choose the unassigned variable with the fewest legal values left in its filtered domain. Also called the most constrained variable heuristic, or "fail-fast" ordering.

MRV needs filtering to be running — "values left in its domain" is only meaningful if someone is crossing values off. In practice MRV is always paired with forward checking or AC-3.

Answer — why min rather than max?

Because you must satisfy every variable, so the only question is when you find out you cannot. Ordering never changes whether a solution exists; it changes the depth at which failure becomes visible. So put the variable most likely to fail as close to the root as possible.

Reason 1 — the pruned subtree is exponentially bigger near the top. If a variable is doomed and you discover it at depth $k$, you discard a subtree of about $d^{\,n-k}$ leaves. Discovering at depth 1 discards $d^{\,n-1}$; discovering at depth $n-1$ discards $d$. Concretely in Australia: suppose SA is unsatisfiable given the current filtering. Assign SA first and you fail once. Assign it last and you re-discover the same failure at the bottom of every branch above it — up to $3^5 = 243$ separate times, each after five wasted assignments.

Reason 2 — the branching factor at this node is smallest. The node you are about to expand has exactly $|D_X|$ children. Choosing the smallest $|D_X|$ makes the tree narrowest at the top, and a tree that is narrow at the top and wide at the bottom has far fewer nodes than one shaped the other way round. (Compare $2 \times 9$ with $9 \times 2$ — same product, but the first shape reaches its 18 leaves through 2 internal nodes and the second through 9.)

Reason 3 — the $|D_X| = 0$ case is free. If any variable has an empty domain, MRV selects it (0 is the minimum), and the for loop over its values runs zero times, so we return failure immediately. MRV therefore subsumes the wipeout check for free.

What max remaining values would do: it puts the easy, flexible variables at the top and the bottleneck at the bottom — the worst possible shape. You would branch widely on variables that were never going to cause trouble, then hit the same contradiction over and over at the leaves. It is the correct answer to the opposite question.

Analogy

MRV is the advice "do the hardest part of the exam first" — not because the hard part is more fun, but because if it turns out to be impossible you want to know at minute 5, not minute 85 after you have invested in everything that depended on it. In Sudoku it is the rule every solver already uses: scan for the square with only one candidate left and fill that one, rather than guessing in a square with six candidates.

Tie-breaking. Several variables often tie on domain size — at the very start of Australia, all seven have three values. The standard tie-breaker is the degree heuristic from §5: among the tied variables, pick the one with the most constraints on unassigned variables. In Australia that is SA (degree 5), which is precisely the variable we want at the root.

Value ordering: least constraining value

Definition

Least constraining value (LCV): given a choice of variable, try its values in order of how few options each rules out for the remaining variables — the least constraining value first.

Note that it may take some computation to determine this: to know how many options a value rules out you effectively have to re-run the filtering for each candidate value and count the deletions.

Answer — why least rather than most?

Because you only need ONE value to work. A variable node in the search tree is a disjunction: the subtree succeeds if any child succeeds. Trying values is a search for one that works, so you should try the one most likely to work first — and the value that leaves its neighbours the most options is the one under which solutions are most likely to survive.

What happens if you get it backwards. Choose the most constraining value and you maximise the chance that the first child fails. But failure of that child does not end anything — you still have to go back and try the other values. You have simply guaranteed that the first attempt is wasted. The effort spent on it buys nothing, because the alternatives remain.

Caveat, stated honestly. LCV only helps when you are looking for one solution and a solution exists. If the subproblem has no solution at all, you must try every value regardless, and the order is irrelevant (as is the case when you are enumerating all solutions). LCV is a bet on success; MRV is a bet on failure. Both bets pay off on realistic instances, which is why they are used together.

The chapter in five lines:

Key idea
  • CSPs are a special kind of search problem: states are partial assignments, and the goal test is defined by constraints over subsets of the variables rather than being an opaque function of the whole state.

  • Speed-up 3, structure — exploit the shape of the constraint graph.

Structure — listed, and deferred

The lecture lists structure as the third family of speed-ups and puts it in parentheses: mentioned, not covered. For completeness, here is what is behind the parenthesis. beyond syllabus

  • Independent subproblems. Already used in §5: solve each connected component of the constraint graph separately. Tasmania is the toy case.
  • Tree-structured CSPs. If the constraint graph is a tree (no cycles), the CSP is solvable in $\mathbf{O(n d^2)}$ with no backtracking whatsoever. The method: pick a root, order the variables so parents precede children, run REVISE on each arc (parent → child) backwards from the leaves to the root, then assign forwards from the root — every value you meet is guaranteed to extend. Guided problem 2 was a small instance of exactly this, which is why arc consistency alone solved it.
  • Cutset conditioning. If the graph is nearly a tree, find a small set $S$ of variables (the cycle cutset) whose removal leaves a tree, enumerate all $d^{|S|}$ assignments to $S$, and solve the resulting tree in $O(nd^2)$ each time. Total $O(d^{|S|} \cdot n d^2)$ — exponential only in the cutset size, not in $n$. For Australia, removing the single variable SA leaves the path WA–NT–Q–NSW–V plus the isolated T, so $|S| = 1$ and the whole instance is solvable in $O(3 \cdot 7 \cdot 9)$ steps. That is the formal reason SA kept showing up as the bottleneck.
  • Tree decomposition. The general version, parameterised by treewidth: a CSP with treewidth $w$ is solvable in $O(n d^{\,w+1})$.

What this chapter leaves for later

  • Local search for CSPs (min-conflicts hill climbing) — start from a complete, broken assignment and repair it. It is the method that really solves million-queens, and it is not in this lecture.
